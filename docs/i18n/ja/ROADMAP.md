## 成熟度

何に頼れるのかを、そのまま書きます。

| 部分 | 成熟度 | それが意味すること |
|---|---|---|
| AWI 契約 | **安定** | v1 の内側では追加のみ。破壊的変更は新しいメジャーバージョンへ |
| ブレイン中核（オーケストレーター、セッション、LLM アダプタ） | **ベータ** | 動く。ただし内部はリリース間で動く |
| 信頼モデル | **ベータ** | 規則は固まった。その周りの表層はまだ |
| 各ワールド | **実験的** | それぞれ 1 つのことを試すために存在し、その中身が変われば書き直される |

**これは研究用プロトタイプであって、本番向けのフレームワークではありません。** セキュリティ認証は
なく、実機を動かしたこともありません。[SECURITY.md](SECURITY.md) を参照してください。

## 未解決の目標

### R1 · 部屋の同定に確証バイアスがある

目標の部屋 5 つを 1 回ずつ：2 つ正解、2 つ不正解、1 つは未完。v1.0 で計測し、以後変わっていません。

面白いのは、それが*何ではないか*です。疑っていたのは「0.38 m の高さではキッチンと浴室が似て見える」
ということで、人形を足した理由のひとつもそれでした。ところが 1.25 m からはコンロもレンジフードも
はっきり見えているのに、やはり浴室だと言います。同じ戸口に向かって、モデルはいま探している部屋に
合う筋書きのほうを組み立てるのです。

狙いは知覚ではなく合否の判定基準のほうです。まず記述させ、分類はその後にする。そして
「見えている、だから着いた」と言ってよい範囲を締めること。

### R2 · プロンプトの言語切り替えは計測されていない

v1.1 で、モデルが読むプロンプトはすべて中国語から英語に書き直されました。システムプロンプト、
ツールの説明、state のブロック、各ワールドのガイダンス。

**それは挙動の変更であり、決着をつけるはずのベンチマークは再実行されていません。** 理由は
`src/prompts.py` に書いてあります。命令チューニングされたモデルは主に英語で訓練されており、
英語のツールスキーマを中国語のプロンプトで包むと文脈が混ざります。文献での効果は数パーセントと
小さく、ときに負の値になります。

借りは、同じ 5 部屋を前と後で並べること。それが出るまで「ここでは英語のほうがよい」は仮説であって
結果ではありません。悪くなっていたら、巻き戻す先はファイル 1 つです。

### R3 · プロンプトインジェクションは緩和されただけで解決していない

ワールドのガイダンスは囲われ、指示ではなく資料としてラベルを貼られ、長さも制限されます。
ハードルは上がります。敵対的な意図がないかを検査する仕組みはなく、そうした検査が信頼できるものに
なる見込みもありません——これは分野全体の未解決問題です。

効いている防御は `anima world add` での人間の承認であり、それはその人が実際に能力マニフェストを
読んだときにだけ効きます。[SECURITY.md](SECURITY.md) 第 2 節を参照。

### R4 · フロントエンドの npm ツリーに深刻度の高い CVE が 4 件

`next`、`postcss`、`sharp`、`@tailwindcss/postcss`。いずれも範囲内で修正可能です。ビルド時のもので、
ブラウザのバンドルには届きませんが、実在し、既知です。

未着手なのは、Next のメジャー更新には画面を目視で確認する作業が要るからで、それはリリースとは
別の仕事だからです。

### R5 · チェスの規則ライブラリは「十分速い」であって「速い」ではない

`packages/anima-chess` は局面によって python-chess の 2〜4 倍遅い——それが存在理由である深さ 3 の
助言探索には足りていますが（上限 1.5 秒に対して 1.27 秒）、それより深いものには足りません。

判明しているコストは、Zobrist ハッシュを push のたびに差分更新ではなくゼロから作り直している点です。
これは意図した選択として `push()` に記録してあり、置換表を入れる日にまず変えるべき箇所です。

### R6 · 中国語がまだいくつかの表層に残っている

v1.1 の言語整理で、モデルが読むものと、CLI とウェブアプリが見せるものはすべて英語になりました。
4 か所だけ、それぞれ理由があって残っています：

- `world/sim-chess/awi_mcp.py` —— MCP のリソースとプロンプトの説明。このファイルは
  **4 か所にバイト単位で同一のコピー**として存在し、うち 3 つはテストが固定しています。
  4 つの文字列を変えるとは 4 つすべてを足並みそろえて変えることであり、
  リリース当日にやることではありません。
- `src/dev_turn.py` —— 開発用のハーネスで、出荷されるコマンドではありません。
- `src/config.py` のフィールド説明とオーケストレーターのログ 2 行 —— 内部専用。かつてこれらが
  供給していたパネルのヒントは、いまは分離されていて英語です。

見つかったのはソースを読んでではなく、wheel を入れて動かしてです。見つけたときのスキャンは
残す価値があります。AST を歩き、docstring でない文字列定数を集め、CJK を探す。

### R7 · UI の陳腐化チェックは、肝心なところで目が見えていなかった

`anima serve` は同梱のウェブアプリがいつビルドされたかを表示します。画面を作り直さずに
wheel を固めてしまったときに気づけるようにするためです。それはビルド時刻を `index.html` の
mtime から読んでいました——そして `pip install` は mtime をインストール時刻に書き換えるので、
**インストールされたコピーはどれも「たったいまビルドされた」と主張していました**。
このチェックが働いていたのは開発用チェックアウトの中だけ、つまりいちばん要らない場所だけでした。

リポジトリでは修正済みです（ビルドが `.build-time` ファイルを書き、それが mtime より優先され、
テストが固定します）。**PyPI 上の 1.1.0 wheel はまだ古い挙動のままです**——報告されるビルド時刻は
そのインストール時刻です。そのリリースの他の部分には影響しません。同梱された画面は、タイムスタンプを
信じるのではなく、ページ自体を読んで検証しました。

見つかったのは、PyPI から 1.1.0 を入れて、実際のビルドより 6 時間あとのビルド時刻を主張しているのに
気づいたからです。

### R8 · 各翻訳は母語話者に読まれていない

日本語のインターフェース項目 231 件を、メンテナーが独立したレビューの助けを借りて翻訳しました。
そのレビューは 22 件の実際の欠陥を見つけています——用語がひとつに潰れていた、造語がひとつ、
翻訳の途中で名詞が落ちた文が 2 つ、そして切り詰められるほど長いサイドバーのラベルが 4 つ。
これらは修正済みです。日本語・フランス語・スペイン語の根幹ドキュメントはその後に、同じやり方で
作られました。フランス語とスペイン語は**ドキュメントのみ**で、インターフェースが話すのは
英語・中国語・日本語です。

修正されていないのは、**それらの言語を話す人が誰ひとりとして、そのどれも読んでいない**という
ことです。レビューをしたのはいずれも人ではなく別のモデルでした。用語は言語ごとに少なくとも
一貫しており（world = ワールド / monde / mundo、ground truth = 真値 / vérité terrain /
verdad de referencia）、プレースホルダーは 1 つも欠けていません。だから**初稿としては使える**
——ただし主張はあくまで「初稿としては使える」であって、「正しい」ではありません。
英語と中国語はメンテナー自身の言語であり、この但し書きは付きません。

### R9 · 言語切り替えのないページが 2 つある

`/awi` と `/session-logs` はサイドバーのない全画面ページとして描画され、切り替えはそのサイドバーに
あります。直接開くと `localStorage` にある言語をそのまま引き継ぎ、変える手段がありません。
通常の経路である本体アプリから辿った場合は問題ありません。

直していないのは、正直な選択肢がどちらも問題より大きいからです。2 つのルートが共有するレイアウトに
切り替えを置くか、あの 2 ルートは副次的な画面だと割り切るか。

### R10 · 依存 9 件に上限がなく、そのうち 1 つはまた CI を壊す

1 週間のうちに 2 度、誰も一行も変えていないのに緑のリポジトリが赤くなりました。ruff 0.16.0 が
既定のルールセットを広げ（手つかずのコードに 205 件の指摘）、mcp 2.0.0 が
`mcp.server.fastmcp` を移動して、`services/boardgame_engine/app.py` がそれを直接
import していました。どちらも上限を付けました。実行時依存の 9 件には付いていません。

**これは見落としではなく意図です。** anima-zero は人がインストールするライブラリであり、
公開されたライブラリの上限は*利用者側の*依存解決問題になります——しかも迂回できません。
ここでの規則は、壊れると実証されたものだけに上限を付けること。そして壊れた 2 件には共通の形が
ありました。どちらも、公開され文書化された表面より深いところに依存していたのです
（内部サブモジュール、ツールの既定設定）。その基準で見ると、残る 9 件はどれも当てはまりません。

なので方針は、3 件目が壊れたときに上限を付けることです。CI が赤くなるのと 2 行の変更で
かかるのはおよそ 10 分。投機的な上限は、これから先の利用者全員にコストを課します。
そして赤い実行には情報があります——上流の API が動いたことを、そうやって知るのです。

もし中断のほうが割に合わなくなったら、直し方は `pyproject.toml` に上限を増やすことではなく、
CI 専用の constraints ファイルです。CI は固定バージョンを入れ、公開されるパッケージは寛容なまま。
それにも代償があります——保守するものが増え、上流が変わったと気づく瞬間が*遅れます*。
この理屈は依存リストの先頭に書いてあります。上限を足したくなった人が、ちょうどそこに立つからです。

## やらないこと

「やらない」と言うのもロードマップの一部です。

- `anima-chess` での **Chess960、PGN、定跡書、UCI** —— python-chess を使ってください。
  どれについても向こうのほうが優れています。
- **curl 一発のインストーラ。** ANIMA は Python であり、そのワールドも Python です。これを動かす人は
  すでに Python を持っています。`uv tool install` は、正直に保つべき配布経路をもう 1 本増やすことなく、
  同じ「コマンド 1 つ」の体験を与えてくれます。
- **特定のワールドについてブレインを賢くすること。** タスク固有の知識はワールドに住みます。
  オーケストレーターがチェスとは何かを覚えた瞬間に、フレームワークだという主張は終わります。
